# ADR-004: Workspace IDE 分阶段架构

- **状态**: Accepted
- **日期**: 2026-09-12
- **决策人**: ADui

---

## 背景

REQUIREMENTS §13 定义了 Workspace IDE（Toolbar / Explorer / Monaco Editor / Agent 面板 / 底部
Panel），是平台从"运行观测"升级为"工作环境"的关键阶段。它涉及文件访问、编辑器、Git、
终端与 Runner 集成，是一个跨 API / Web / Desktop / Runner 的大阶段，需要先固定架构决策，
避免各端各长一套。

## 决策

1. **文件访问的唯一边界**：所有文件读写走 `@adui-forge/tool-sdk` 的
   `resolveInWorkspace`（三层防御：路径遍历 / symlink 逃逸 / 不存在泄露）。API 层的
   Workspace 模块与未来的 Runner 文件服务共用同一边界函数，不出现第二套路径校验。
2. **Workspace 根来源**：Web/云端由 API 的 `FORGE_WORKSPACE_ROOT` 决定；Desktop 本地模式
   由 Local Runner 决定并通过 Tauri capability 暴露（后续 ADR）。两种模式对前端暴露
   **同一套 REST 形状**（`/workspace/tree`、`/workspace/file`），前端无感切换。
3. **编辑器**：Web 端采用 Monaco（技术栈既定），通过路由级 lazy chunk 加载（已在
   ADR-001 的 code-splitting 架构内），不进首屏。Monaco 只做编辑器视图，文件树/状态
   管理由平台组件承担。
4. **写操作安全**：单文件大小上限（1 MiB）、二进制扩展名拒绝写入文本接口、写入不经过
   Sandbox（文件边界即沙箱）；Git / Shell 类操作仍强制走 Sandbox + approval，与文件编辑
   分离。
5. **分阶段交付**：
   - 阶段 1（本 ADR 随附）：Workspace 文件 API（tree / read / write）+ 边界测试；
   - 阶段 2：Web 文件树 + Monaco 编辑器页（懒加载）；
   - 阶段 3：Desktop Local Runner 接管同一 REST 形状；
   - 阶段 4：Git 面板 / 终端 / Agent 面板集成进 IDE 布局。

## 被否决的备选方案

| 方案                                 | 否决原因                                                             |
| ------------------------------------ | -------------------------------------------------------------------- |
| API 内新写一套路径校验               | 与 tool-sdk 边界逻辑重复，违反"边界唯一"原则（AGENTS.md §40）        |
| Web 直连本地文件系统（Tauri fs）     | 绕过 REST 形状，桌面/云端前端分叉，违背 §17/§18 复用原则             |
| 全量引入 VSCode Server / code-server | 体量与安全面过大，与平台 Agent 体系无法融合                          |
| 文件写入也走 Sandbox 执行            | 文件边界已足够；进程类操作才需要 Sandbox（Sandbox First 的准确范围） |

## 后果

- 阶段 1 起平台具备文件观测/编辑能力的后端基础；`FORGE_WORKSPACE_ROOT` 未配置时
  Workspace 模块显式降级（409），不静默。
- 前端将新增一个重依赖（Monaco），通过懒加载隔离在 Workspace 路由 chunk 内。
- Local Runner 落地后需要第二个 ADR 固定 Runner 进程模型与 Tauri capability 清单。
